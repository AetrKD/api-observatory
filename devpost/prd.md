# GitHub 저장소 외부 API 현황 분석 도구 — 제품 요구사항

웹 애플리케이션 개발·유지보수자가 공개 저장소의 외부 API와 호출 위치를 파악하는 도구. 제품명은 임시 설명명이다.
출처: scope.md > The Unique Kernel, Who It's For, The Core Loop.

## The Core Journey
1. GitHub 계정으로 로그인한다.
2. 이전에 등록한 저장소 목록을 확인한다. 처음이면 목록은 비어 있고 새 저장소 추가가 가능하다.
3. 새 저장소 추가에서 공개 GitHub 저장소 주소를 입력한다.
4. 기본값으로 즉시 분석한다. 계정 설정에서 자동 분석을 끈 경우 등록만 하고 수동 실행한다.
5. 분석 중에는 현재 단계와 실제 읽은 파일 수를 표시한다.
6. 완료하면 왼쪽 API 목록에서 항목을 선택하고 오른쪽에서 상세 정보를 확인한다.
7. 같은 계정으로 다른 기기에 접속해 목록·설정·저장된 결과를 다시 본다. 필요할 때 재분석한다.
출처: scope.md > The Core Loop, What "Working" Looks Like. 계정과 동기화는 범위 승인 이후 사용자가 명시적으로 추가한 요구사항이다.

## Screens and Layout
- 로그인 진입: GitHub 계정으로 접속한다.
- 저장소 목록: 등록한 저장소와 새 저장소 추가 버튼. 주소 입력을 제공하고 저장소의 분석 결과로 이동할 수 있다. 추가 입력의 모달/별도 화면 여부는 구현 배치 선택으로 남긴다.
- 분석 결과: 왼쪽에 API 목록, 오른쪽에 선택한 API 상세. 상세에는 API 식별 정보, 호출 파일과 관련 기능 및 근거, 등록된 점검 대상의 최근 점검 결과·시점 또는 미설정 이유를 표시한다. 분석 시점과 최근 시도 상태를 구별한다.
- 계정 설정: 등록 직후 자동 분석의 켜기/끄기. 기본값은 켜짐이다.

## Features and Behavior

### GitHub 로그인과 계정별 동기화
GitHub 계정에 저장소 목록, 자동 분석 설정, 분석 결과를 연결한다. 같은 계정은 다른 기기에서 동일 정보를 볼 수 있고 다른 계정의 개인 목록과 결과는 접근할 수 없다. 로그인 실패 시 이유와 다시 시도할 동작을 제공한다.

### 저장소 등록과 분석 실행
공개 GitHub 저장소 하나의 주소를 입력해 등록한다. 기본 자동 분석 또는 설정에 따른 수동 분석, 기존 저장소 재분석을 지원한다. 사용할 수 없는 주소·비공개/접근 불가 저장소는 사유와 함께 실패로 안내한다.
출처: scope.md > The POC Boundary, Explicitly Cut.

### API 목록과 상세
탐지 가능한 외부 API를 모아 보여준다. 선택한 API의 호출 파일, 관련 기능, 코드 근거를 오른쪽에서 확인한다. 추론이 어려운 기능은 확인 불가 또는 불확실하다고 표시한다. 코드 분석 결과와 실제 점검 결과를 구분한다. 점검 기준 통과를 서비스 전체 정상으로 해석하지 않는다.
출처: scope.md > The Unique Kernel, The POC Boundary.

### 분석 상태와 실패
분석 중에는 현재 단계와 실제 읽은 파일 수를 표시한다. 실패는 “분석 실패”와 사유를 표시한다. API 미검출도 실패로 안내하되 “지원하는 탐지 방식으로 외부 API를 찾지 못했습니다”처럼 표현하고, API가 없다고 단정하지 않는다. 실제 사유를 알 수 없을 때는 추측해 단정하지 않는다.

### 결과 저장과 교체
저장소마다 마지막 성공 결과 하나 및 그 분석 시점, 최근 분석 시도의 상태와 시점·실패 사유를 보관한다. 성공 시 기존 성공 결과를 새 결과로 교체한다. 실패·미검출 시 이전 성공 결과는 유지하고 최근 시도가 실패했음을 별도로 표시한다. 이전 성공 결과가 없으면 실패 안내만 표시한다. 결과 이력 여러 개는 보관하지 않는다.

## Acceptance Criteria
- 같은 GitHub 계정으로 다른 기기에 접속하면 등록한 저장소, 자동 분석 설정과 마지막 성공 결과가 보인다.
- 다른 계정으로 접속하면 해당 사용자의 저장소 목록과 저장 결과가 보이지 않는다.
- 자동 분석 기본값에서 공개 저장소 등록 직후 “분석 중”이 보인다. 끈 경우 등록만 되며 수동 실행이 가능하다.
- 알려진 외부 API 호출이 있는 지원 예제 저장소를 분석하면 API와 실제 호출 파일·관련 기능 근거가 대응한다.
- 왼쪽 API를 선택하면 오른쪽 상세가 해당 API로 바뀐다.
- 점검 미설정 대상은 확인 불가와 이유를 표시한다. 설정된 대상은 최근 점검 시점과 기준 통과 여부를 표시한다.
- 실패와 미검출에서 실패 안내와 사유가 보인다.
- 성공 후 재분석 실패 시 이전 성공 결과·분석 시점과 최근 실패 사유가 함께 보인다. 다음 성공 시 최신 성공 결과로 교체된다.
출처: scope.md > What "Working" Looks Like 및 후속 사용자 결정.

## States and Boundaries
- 최초 사용: 등록 목록이 비어 있으며 새 저장소 추가가 가능하다.
- 등록만 완료: 자동 분석을 끈 경우 아직 분석하지 않았음을 구분하고 수동 실행이 가능하다.
- 분석 중: 단계와 파일 읽기 진행 수를 표시한다. 전체 예상 시간이나 추정 퍼센트는 표시하지 않는다.
- 분석 성공: API 목록과 선택 상세, 성공 분석 시점을 표시한다.
- 분석 실패/미검출: 실패 사유를 표시한다. 이전 성공 결과가 있으면 오래된 결과임을 구분해 유지한다.
- 로그인/저장 실패: 실패 이유를 안내하고 저장되지 않은 정보를 저장된 것으로 표시하지 않는다.
- 공개 저장소만 분석한다. 로컬 실행 환경은 연결하지 않는다. 사용자가 점검용 인증 정보를 별도로 등록할 수 있다. 모든 외부 API 탐지를 보장하지 않는다.

## Product Decisions
- 계정별 동기화: 여러 개발 환경에서 저장소를 반복 등록하는 번거로움을 줄이기 위해 추가했다.
- 등록 직후 자동 분석: 기본 켜짐이며 계정 설정에서 변경한다.
- 왼쪽 API 목록과 오른쪽 선택 상세 배치.
- 분석 결과도 저장하되 최신 성공 결과 하나만 유지한다.
- 재분석 실패는 마지막 성공 결과를 지우지 않고 별도 상태로 표시한다.
- 분석 중은 단계·파일 수, 실패/미검출은 중단 단계와 사유를 포함한다.
- 한국어·영어, Docker Desktop 참고, 지정한 네 가지 색상 사용.
- 무료 DB 서비스(예: Supabase)와 웹 배포 서비스(예: Vercel) 사용 희망. 서비스 선택·이용 조건은 기술 계획에서 검증한다.

## What We're Building
GitHub 로그인, 계정별 저장소 목록·설정·결과 동기화, 공개 저장소 등록, 자동/수동/재분석, API 목록과 호출 위치·관련 기능 상세, 분석 상태와 실패 처리, 마지막 성공 결과 보존, 하루 한 번 API 점검·인증 정보 등록·사용자 지정 판정 조건.

## Deferred From the POC

## Non-Goals

- 기술 계획에서 검증: 무료 DB/배포 이용 조건 및 GitHub 로그인 설정, 계정별 접근 제어, 분석 실행 제한. 계정 기능 추가로 작업량이 늘었으므로 기존 2~4시간 목표 달성 여부를 재평가한다.
- 제품 이름은 현재 임시 설명명이며 출시 전 변경 가능하다.

## Scheduled API Checks
사용자가 발견된 API에 점검 주소와 필요한 읽기 전용 API 키·고정 토큰을 별도로 등록한다. 자동 점검은 기본 켜짐이며, 등록된 점검 대상 전체를 하루 한 번 점검한다. 계정 설정에서 비활성화할 수 있고 이 설정은 같은 계정의 다른 기기에도 유지된다. 이는 저장소 코드 재분석과 별도 기능이다. 정확히 24시간 간격·정각 실행을 보장하지 않으며 실제 예약 방식과 시간 표시를 기술 계획에서 확정한다.

### Check Criteria
- 기본값: HTTP 2xx 응답이면 설정한 점검 기준 통과.
- 사용자는 예상 HTTP 상태 코드와 JSON 응답의 특정 필드 경로·예상 값을 추가 지정할 수 있다. 지정한 조건은 모두 만족해야 통과한다.
- 상태 코드 불일치, 지정 필드 누락·값 불일치, JSON 조건을 설정했으나 JSON으로 해석할 수 없는 응답은 기준 미충족과 구체적 이유를 표시한다.
- 인증·권한 거절, 요청 한도 초과, 서버 오류, 시간 초과·연결 실패를 관찰된 근거로 구분한다. 가능한 원인을 확정된 근본 원인처럼 단정하지 않는다.
- 사용자에게 “설정한 점검 기준 통과 / 미충족 / 실행 실패 / 미설정”을 구별해 보여준다. 최근 점검 시점과 응답 코드·응답 시간을 함께 저장한다. 실패를 과거 통과로 덮어 표시하지 않는다.
- JSON 응답 본문 전체는 저장 요구사항에 포함하지 않는다. 점검 결과 저장과 코드 분석 성공 결과 보존은 구별한다.

### Credential Boundaries
읽기 전용으로 발급한 점검용 API 키·고정 토큰만 지원하며 OAuth 자동 갱신은 제외한다. 모든 공급자의 읽기 전용 권한을 자동 판별할 수 있다고 주장하지 않는다. 사용자는 인증 정보를 교체·삭제할 수 있어야 한다. 저장된 비밀값을 다시 화면에 노출하지 않으며 로그와 결과에 남기지 않는다. 사용자별 접근 제어와 서버 측 암호화, 등록된 전송 대상 제한을 기술 계획에 포함한다. 읽기 전용 키라도 API 요청의 부작용을 보장할 수 없으므로 점검 전용 조회 주소를 사용한다.

### Check Acceptance Criteria
- 자동 점검은 기본 켜짐이다. 등록 대상이 하루 한 번 예약 점검 대상에 포함되고 계정 설정에서 비활성화하면 새 자동 점검이 시작되지 않는다. 같은 계정의 다른 기기에서도 변경한 설정이 유지된다.
- 200 응답은 기본 조건에서 통과한다. 예상 코드 200과 JSON status=ok를 지정했을 때 status=error이면 미충족이다.
- 필드 누락·비JSON·타임아웃·401·429 등에서 관찰 결과와 이유가 구별된다.
- 다른 사용자의 인증 정보를 조회·사용할 수 없으며 저장한 비밀값이 화면·로그·점검 결과에 나타나지 않는다.
- 최신 점검 결과와 시점이 같은 계정의 다른 기기에서도 보이고, 코드 분석 결과의 시점과 구별된다.

### Remaining Check Decisions
기술 계획에서 지원 인증 헤더 방식, JSON 필드 경로 문법·값 타입, 조회 요청 방식, 타임아웃과 호출 제한, 외부 주소 검증·리디렉션 정책, 암호화 키 관리, 예약 실행 방식을 확정한다. 자동 점검의 최초 기본값은 사용자 결정에 따라 켜짐이다.

## Scope Amendment
범위 승인 후 사용자가 GitHub 계정 동기화, 저장 결과, 하루 한 번 실제 API 점검과 인증 정보 등록 및 판정 조건을 추가 요청했다. 이 PRD 초안은 확장한 요구사항의 검토본이며 기존 scope의 실제 점검 제외 결정을 대체하는 변경안이다. 보안·권한의 자동 분석과 장애 주입 테스트는 계속 제외한다. 계정·예약·비밀값 관리까지 포함하면 원래 2~4시간 학습 목표보다 커질 수 있어 기술 계획에서 작업을 분리한다.



## Selected Private Repository Access
사용자 승인 변경: 공개 저장소뿐 아니라 GitHub App을 연결해 본인 GitHub 계정에서 접근을 허용한 비공개 저장소를 분석한다. 이 절이 기존 공개 저장소 전용 제한을 대체한다. 첫 연결 화면은 GitHub 로그인 후 저장소 연결/선택이며 사용자는 GitHub에서 저장소별 읽기 권한을 부여한다. 로그인만으로 비공개 접근 권한이 생기지 않는다.
- 선택·허용된 저장소 목록에서 등록하고 공개 저장소와 같은 분석 화면을 사용한다. 기존 소스·크기·언어 한도는 유지한다.
- 비공개 표식을 표시하고 다른 계정에 목록·코드 위치·분석 결과를 노출하지 않는다.
- 원본 전체 코드는 지속 저장하지 않고 분석 중에만 읽는다. 필요한 호출 정보·파일 위치만 사용자별 결과로 저장하며 비밀값을 마스킹한다.
- 미설치·권한 부족·접근 해제를 구분한다. 접근 해제 시 새로운 분석과 저장된 비공개 결과 조회도 차단하며 권한 재연결을 안내한다.
- 서비스의 연결 해제 시 저장소 토큰 사용과 연결된 점검을 중지한다. 실제 외부 API 점검 주소·키 등록은 별도다.
- 첫 범위는 본인 개인 계정의 선택 저장소이며 조직 저장소·팀 공유·모든 저장소 일괄 권한은 별도 확장으로 남긴다.
확인 기준: 허용한 비공개 저장소만 목록·분석 가능, 다른 사용자·미선택 저장소 거절, 권한 회수 후 과거 결과 조회도 거절. 조직 설치 정책이 필요한 경우 권한을 우회하지 않는다.

## Manual API Recheck
사용자 승인 추가: 등록된 API 점검 대상의 상세 화면에 “지금 재점검”을 제공한다. 저장소 코드를 다시 분석하는 동작이 아니라, 저장된 점검 주소·인증 정보·예상 응답 조건으로 실제 조회 요청을 한 번 수행한다.
- 실행 중에는 점검 중 상태를 표시하고 같은 대상의 중복 실행을 막는다.
- 통과·기준 미충족·실행 실패와 점검 시점·응답 코드·응답 시간을 갱신한다. 수동 실행임을 구분한다.
- 일일 자동 점검 설정이 꺼져 있어도 수동 실행은 가능하다. 수동 실행은 자동 점검 설정과 다음 예약 시간을 바꾸지 않는다.
- 점검 주소가 없으면 실행하지 않고 설정 안내를 보여준다. 인증 누락·권한 회수는 사유를 표시하며 우회하지 않는다.
- API 키 보호·읽기 전용 조회·사용자별 권한·외부 요청 제한을 자동 점검과 동일하게 적용한다.
확인 기준: 저장된 조건으로 한 번 요청, 중복 거절, 조건 판정 후 최신 결과 표시, 자동 점검 꺼짐 상태에서도 수동 실행, 코드 분석 결과는 변경하지 않음.

## Excluded Change Summaries
사용자 결정: 재분석 변경 요약은 이 도구의 현재 범위에 추가하지 않는다. 이전·신규 분석 간 비교나 변경 알림을 구현하지 않으며 최신 성공 분석 하나만 유지한다. 수동 재점검과 저장소 재분석은 서로 다른 기능이다.

## Storage Provider Change
사용자 결정: Supabase 대신 Turso를 사용한다. GitHub 로그인, 선택한 비공개 저장소 연결, 계정별 목록·설정·최신 결과 저장 기능은 유지한다. 공급자 변경만으로 기능 완료를 표시하지 않는다.

## Bilingual Workspace Amendment
- 사용자 요청으로 한국어·영어 전환과 언어 선택 기억을 추가한다. 사용자 코드·저장소명은 원문을 유지한다.
- 왼쪽 메뉴는 분석 → 분석 기록 → 등록된 저장소(로그인 시) → 서비스 정보 → 사용법 순서다.
- 분석 기록은 저장소별 최신 성공 결과와 최근 시도 상태·시각을 보여준다. 과거 결과 누적 저장이나 변경 요약은 추가하지 않는다.
- 상단에 현재 계정과 로그인/로그아웃을 표시한다. 로그아웃 시 개인 결과를 지우고, 로그인·App 연결 실패는 화면 안내 후 재시도할 수 있다.
- 지원 언어·분석 한도·실제 응답 점검과 정적 분석의 차이를 서비스 정보와 사용법에서 설명한다.

- 비로그인 로컬 체험은 요청 스트림으로 단계만 전달하며 새로고침 후 복원은 계정에 등록한 저장소에 적용한다.


## Python, Vue and Analysis Limits — 2026-10-26
- Python의 requests·httpx·urllib 호출을 함수·파일·줄과 연결한다. 별칭·Session·Client/AsyncClient·상수·문자열 조합·단순 f-string을 지원하고 해석 불가 값은 미해결로 표시한다. Python의 다른 SDK와 파일 간 값 추적은 지원하지 않는다.
- Vue의 script·script setup에 포함된 JS/TS를 분석하며 원본 .vue 파일과 줄 번호를 제공한다. 템플릿·스타일과 스크립트 블록 간 값 추적은 제외한다. 외부 script src는 인라인 확장하지 않고 지원 소스 파일이 수집되면 별도로 분석한다.
- 분석 한도는 소스 200개·파일당 400 KiB·전체 10 MiB·120초로 상향한다. 메타데이터와 실제 읽은 크기에 모두 적용하고 초과 시 실패 이유를 표시한다.
- Python·Vue 미검출도 API가 없다고 단정하지 않는다. 코드 읽기 성공과 외부 API 탐지 성공을 구별하며, 최신 성공 결과 보존 정책을 유지한다.


## HTML and WebSocket Detection — 2026-10-26
- .html/.htm의 실행 가능한 인라인 JavaScript 블록을 수집하고 원본 HTML의 파일·함수·줄/열을 제공한다. JSON 데이터·주석·외부 script src·이벤트 속성·비활성 template 내용은 탐지 대상에서 제외한다.
- Jinja if/elif/else/endif와 for/endfor 블록의 가능한 호출을 정적으로 분석한다. 렌더링 조건과 템플릿 값은 실행하지 않는다. 템플릿 값이 섞인 주소는 미해결로 유지한다.
- 브라우저 WebSocket 생성자를 탐지하고 WS로 표시한다. 현재 브라우저 location.host를 사용하는 단순 URL 템플릿은 호스트를 추측하지 않고 내부 경로만 표시한다.
- 이미 App 접근이 허용된 공개 저장소는 기존 계정 연결의 저장소 하나·contents:read 토큰을 사용해 비로그인 요청 제한에 의한 분석 실패를 줄인다. 비공개 권한 검증과 허용하지 않은 공개 저장소의 공개 읽기 경계는 유지한다.


## Live Response Preview — 2026-10-26
- 등록 저장소의 HTTP GET 호출 상세에서 실제 응답 테스트를 누르면 기존 주소 점검 폼에 호출 정보가 준비된다. 상대 경로에는 사용자가 실제 서비스의 공개 HTTPS 주소를 입력한다. 저장소 주소로 실행 주소를 추측하지 않는다.
- 저장과 저장 후 응답 테스트를 구분한다. 후자는 점검 대상을 저장하고 즉시 수동 GET 요청을 실행한다. 비활성 대상은 저장만 가능하다. 기존 읽기 전용 키/정상 응답 기준과 수동 점검 간격을 유지한다.
- HTTP 코드·시간·판정 이유와 JSON/텍스트 본문 미리보기를 표시한다. 바이너리는 본문 미리보기에서 제외한다. 민감 키와 등록 자격값은 가려 표시하고 미리보기는 16 KiB로 제한한다.
- 응답 본문은 수동 실행 응답에서만 제공하며 DB에 보관하지 않는다. 새로고침·메뉴 이동 후 본문은 다시 점검해야 볼 수 있다. 자동 점검과 결과 보관은 기존 상태/이유/코드/시간 메타데이터만 사용한다.


## Project-Level Automatic Responses — 2026-10-26
- 프로젝트 상단에 선택 입력하는 배포 주소와 접힌 공통 인증·자동 조회 설정을 둔다. 주소가 없으면 코드 분석만 정상 사용한다. 저장하고 응답 조회를 누르면 API별 등록 없이 확정된 같은 도메인의 GET 응답을 표시한다.
- 설정은 계정별로 저장한다. 프로젝트 열기·재분석 후 자동 조회는 기본 켜짐이며 끌 수 있다. 최근 5분 결과를 재사용하고 전체 새로고침을 제공한다. 재분석은 같은 커밋이어도 새 분석 시점에 맞춰 갱신한다.
- 왼쪽 목록은 호출 경로와 HTTP 코드/연결 실패/조회 제외를 표시한다. 오른쪽은 실제 요청 주소·시간·HTTP 상태·본문 미리보기를 표시한다. 기본 선택은 테스트 가능한 첫 GET 호출로 한다.
- 공통 키는 배포 origin에만 전송한다. 다른 도메인·미해결 주소·POST/삭제/WebSocket은 이유와 함께 자동 조회에서 제외한다. 한 번에 주소 20개까지, 계정당 30초 간격으로 실행하며 대기 시 자동 재시도한다.
- 분석 완료 안내는 한 줄로 축소하고 프로젝트 이름·재분석 작업을 모은다. 기존 등록 주소/개별 정상 판정/예약 기능은 고급 영역으로 접는다. 자동 응답 조회의 기본 판정은 HTTP 2xx 수신이며 본문 내용의 정상 여부를 보장하지 않는다.

## Public Source Efficiency and Response Format — 2026-10-26
사용자 승인으로 공개 소스의 파일별 REST 호출을 커밋 고정 원문 다운로드로 바꾸고, 기존 로그인 인증으로 공개 메타데이터를 조회한다. 새로운 권한은 요청하지 않는다. 프로젝트 공통·개별 점검에서 서버 기본값/JSON/텍스트/HTML의 Accept 형식을 선택·저장하며 변경된 프로젝트 형식은 이전 캐시를 무효화한다. HTTP 200만으로 JSON 반환을 보장하지 않으며 JSON 조건 판정은 개별 점검에서 지원한다. 비공개 선택 저장소 접근 제어와 점검 안전 경계는 유지한다.
